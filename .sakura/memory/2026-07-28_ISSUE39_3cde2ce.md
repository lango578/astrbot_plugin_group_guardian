## 1. 分类与优先级准确性

### 分类

将其分类为 `question` **在当前主分支已经实现需求的前提下可以成立，但不完全准确**。

原始 Issue 明确提出“开放自定义功能”，从提交时的性质看应属于：

- `enhancement` / feature request

在确认功能已经落地后，当前处置可以转为：

- 告知配置入口；
- 补充文档；
- 验证功能是否满足用户场景；
- 关闭为 completed/resolved。

因此更准确的表达应区分两个时间维度：

- **原始诉求分类：`enhancement`**
- **当前处理动作：功能已实现，以 `documentation` 或答疑方式解决**

如果分析系统要求只给一个“当前分类”，依据项目记忆中“功能已存在归 `question` + `documentation`”的规则，`question` 尚可接受；但应明确这并不意味着原 Issue 本身是普通咨询。

### 优先级

`low` 对“当前剩余工作量”基本合理，但对原始问题影响评价偏低。

Issue 涉及：

- AI 误判后禁言；
- 入群申请误判为广告引流；
- 审核策略缺少用户控制。

这类问题可能直接造成误罚和正常用户无法入群。按照现有项目经验，“误罚及核心审核配置失效”通常至少应考虑 `medium`，广泛发生时甚至可到 `high`。不过当前并没有误封比例、影响群数量或复现样本，不能仅凭“误封严重”直接判为高优先级。

更合理的结论是：

- **需求尚未实现时：`medium`**，若证实默认配置导致普遍误罚，则提升为 `high`；
- **当前主分支已实现后：`low`**，仅剩验证、说明和回归测试。

原分析应明确“优先级是基于当前代码状态，而非原始影响”。

## 2. 标签推荐质量

### `question`

置信度 `0.91` 偏高。原文没有询问如何使用，而是在请求新增配置能力。只有在确认该功能已于 Issue 提交后或当前版本实现，并准备通过回复告知用户时，`question` 才合适。

建议将置信度降至约 `0.7～0.8`，并说明是**当前处置标签**。

### `documentation`

`documentation` 较贴切，尤其是以下情况：

- 功能已有但入口不明显；
- README 没有清晰说明全局与单群配置优先级；
- 没有解释空值恢复默认规则；
- 没有说明用户只能覆盖审核标准，不能破坏固定 JSON 输出协议。

`0.82` 基本合理，但前提是确实存在文档缺口。分析中同时说 README 已记录，因此需要进一步指出“现有文档具体缺少什么”，否则该标签的必要性会下降。

### 可能遗漏或需要避免的标签

- 若仓库存在 `enhancement`，可以保留它来表示 Issue 的原始性质，或在关闭前不再添加。
- 若仓库存在 `resolved`、`implemented`、`completed` 一类标签，可能比 `question` 更准确。
- 不建议添加 `bug`：目前没有证据表明自定义配置失效，只是默认策略不适合部分群。
- 不建议添加 `good first issue`：即使只剩测试，也涉及按群配置、WebUI、提示词拼装、JSON 降级等多条路径。
- 不建议添加 `help wanted`：作者未勾选愿意提交 PR，且主体功能已实现。

最重要的是：**分析没有核验仓库实际标签列表**。应区分：

- 语义上推荐的标签；
- 仓库中实际可添加的标签。

## 3. 可行性判断质量

### 做得较好的地方

可行性分析比一般的“可以增加配置项”更扎实，具体识别了：

- `_conf_schema.json` 中的自定义审核标准；
- `moderation.py` 按群读取和拼装提示词；
- 固定保留 JSON 输出格式、消息边界和上下文；
- `web.py` 的配置映射；
- 入群审核中的 `join_reject_use_lexicon`；
- 通过词优先；
- `join_llm_custom_prompt`；
- LLM 失败时回退本地规则；
- 已有测试覆盖入群自定义标准和按群空值覆盖。

这些信息说明分析确实参考了实际实现，而不是停留在方案猜测。

### 需要改进的地方

#### 1. 应明确“自定义提示词”的能力边界

当前实现似乎允许用户替换的是**审核标准部分**，并非完全接管整段系统提示词。框架仍然追加：

- JSON 返回格式；
- 待审消息边界；
- 上下文；
- 可能还有固定的安全约束。

这与用户口中的“自定义提示词”并不完全等价。分析应明确：

> 当前实现支持自定义审核标准，而不是覆盖完整 Prompt；这是为了保证输出可解析和审核链路稳定。

否则可能过早判断“需求已完全落地”。

#### 2. 缺少版本和提交证据

应补充：

- 相关字段首次出现在哪个提交或版本；
- CHANGELOG 哪一条关联 #39；
- 当前发布版是否已包含，还是只在主分支存在。

如果功能只存在于主分支，而用户使用的是已发布版本，就不能简单回复“已经实现”，还需要告知升级渠道或发布时间。

#### 3. 风险分析可以更完整

除了无效 JSON 降级，还应检查：

- 用户自定义标准是否可能覆盖或诱导模型忽略固定输出协议；
- Prompt 中是否正确分隔用户配置、上下文和待审消息，避免提示注入；
- 全局配置与单群配置的优先级；
- 空字符串、仅空白字符串、缺失字段的语义是否一致；
- WebUI 保存后是否发生类型转换、裁剪或换行丢失；
- LLM 超时、异常和并发限制是否复用统一安全调用；
- 降级时是回退本地候选判断、默认标准，还是执行保守处罚，避免行为不透明。

#### 4. 工作量应拆分

“剩余工作量较低”总体合理，但应分层：

- **最小处置**：确认配置入口、回复用户、关闭 Issue，约几十分钟；
- **文档补充**：说明消息审核与入群审核的配置差异、按群覆盖和空值语义；
- **回归测试**：默认标准、自定义标准、按群覆盖、无效 JSON、模型异常；
- **外部冒烟**：至少使用一个实际模型验证输出格式和 WebUI 保存行为。

测试与模型冒烟存在环境和提供商成本，不能完全等同于简单文档工作。

## 6. 经验教训

### 1. 区分原始分类、当前状态与处置动作

功能建议在实现后，不会改变其历史性质。分析时应分别描述：

- 原始类型：enhancement；
- 当前状态：implemented；
- 下一步动作：答疑、文档、测试、关闭。

避免把“已经实现”直接等同于“原 Issue 是 question”。

### 2. 区分影响优先级与剩余工作优先级

审核误罚本身可能具有较高影响，但功能落地后只剩文档和验证，当前工作优先级可以低。应显式说明评价基准，不能仅用“剩余工作少”反推原始问题影响小。

### 3. “自定义 Prompt”必须核对能力边界

要确认用户能自定义的是：

- 完整系统提示词；
- 审核标准片段；
- 输出格式；
- 示例；
- 上下文范围；
- 还是仅某个模板变量。

对于需要结构化 JSON 的审核链路，通常应允许自定义规则，但固定保留输出协议和消息边界。回复用户时必须说明这一限制。

### 4. 重复检测必须只有一个最终结论

正文、结构化字段和关闭建议必须一致。每个候选至少给出：

- Issue 编号和标题；
- 核心诉求摘要；
- 相同点；
- 不同点；
- 最终是否重复。

本次应先核验 #12，再决定是否认定；不能同时写“不建议重复”和“可能重复”。

### 5. 功能已落地仍需确认发布状态

“主分支已有”不等于“用户当前版本可用”。应检查：

- 引入版本；
- 最新 Release 是否包含；
- 配置迁移是否自动完成；
- WebUI 是否需要重启或刷新 Schema；
- 老配置是否保持兼容。

### 6. 审核配置测试应覆盖语义和降级

建议形成固定回归矩阵：

- 默认标准；
- 全局自定义标准；
- 单群覆盖；
- 单群空值恢复默认或继承全局；
- 多行文本和特殊字符；
- 模型返回非法 JSON；
- 模型超时或异常；
- 自定义标准尝试破坏输出协议；
- 入群通过词、通用词库和 LLM 二审的优先级。
