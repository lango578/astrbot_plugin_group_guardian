# Issue 响应剧本

将高频审查场景转成可复用处置动作。

## 1. 功能已经存在

**判定**：代码、README 或 WebUI 已能满足核心诉求。

**处置**：
1. 分类 `question` + `documentation`，低优先级；
2. 告知准确入口、命令和配置开关；
3. 排查用户是否因默认关闭、权限或版本差异而不可见；
4. 若多人重复咨询，改善 README、FAQ、`/help` 或别名；
5. 只有额外交互方式是独立诉求时，另拆 enhancement。

不要因“技术上还能扩展”给原 Issue 混标 `enhancement`。

## 2. 截图或描述不足

1. 先归 `question`/`needs-more-info`，不猜测 bug；
2. 剥离情绪化措辞，提取可验证需求；
3. 根据代码枚举有限候选位置；
4. 请求粘贴文字、错误栈、协议实现、版本、复现步骤；
5. 信息确认后再转 `bug` 或 `enhancement`。

推荐回复：
> 当前截图内容无法可靠读取。请粘贴需修改的文字或错误信息，并说明出现页面/命令、AstrBot 与 OneBot 实现版本及复现步骤。

## 3. 垃圾推广

- 纯外链推广、贬损对比且无技术内容：`other` + `invalid`；仓库有 `spam` 时优先使用。
- 跳过技术可行性分析，直接关闭。
- 重复提交：警告、自动过滤或限制用户。
- 评论区争吵：锁帖并清理侮辱性评论。

## 4. 权限或审核误罚

- 权限绕过、多入口授权不一致：倾向 `bug` + `high`。
- 正常用户被误禁/误拒、配置开关失效：按业务伤害定高优先级，不按修复行数降级。
- 先画入口和决策顺序，再给最小修复；可选新开关另列高级方案。

## 5. 重复检测输出模板

```text
范围：open + closed Issues
关键词：A、B、错误码 C
候选：#N（触发/根因/修复点摘要）
对比：相同点；不同点
结论：重复或不重复；置信度 X
```

置信度低于 0.7 不输出候选。最终只能有一个结论，不得同时写“未发现”与“可能重复”。

## 6. 协作标签

- `help wanted` 需结合提交者贡献意愿；未表示愿意 PR 时通常仅 0.5～0.6。
- 多文件、权限、配置兼容、框架 Schema、外部依赖任务不标 `good first issue`。
- 推荐前核验仓库真实标签；语义标签与可实际添加标签分开说明。
